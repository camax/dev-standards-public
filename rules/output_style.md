# 📝 Output Style & Communication Protocol

## 1. 簡潔かつ効果的なコミュニケーション

### 1.1 結論ファースト (Conclusion-First Output)
* **概要**: エージェントからユーザーへの報告は、常に最も重要な結論や結果から記載し、ユーザーが瞬時に状況を把握できるようにします。
* **ルール**:
  * 回答の冒頭で「何が完了したか」「現在のステータスはどうなっているか」を一文で簡潔に提示する。
  * 背景や経緯、詳細な技術的プロセスは、結論の後に見出しを分けて記載する。

### 1.2 冗長な背景説明・コード解説の排除
* **概要**: ユーザーはコード自体や正確な動作結果に関心があります。エージェントがプログラムの動作を日本語で1から10まで冗長に解説することは避けます。
* **ルール**:
  * 実行したコードの全解説は行わず、重要なロジックの変更点や検証結果の数値のみに絞る。
  * 「〜という処理を行い、〜を返します」といったトリビアルなコードの説明は最小限にする。

## 2. コード提示プロトコル

### 2.1 Diff / パッチ形式を優先したコード提示
* **概要**: コード変更内容を提示する際は、ファイル全体をそのまま貼り付けるのではなく、変更箇所のみを `diff` ブロック形式で提示します。
* **ルール**:
  * 行数の多いファイルの一部を変更した場合は、必ず前後数行を含む差分（`diff`）形式で変更箇所を提示する。
  * 差分の追加行は `+`、削除行は `-` を明示する。
* **例**:
  ```diff
  - const sagawaCarrierId = '1';
  + const sagawaCarrierId = '2'; // 佐川急便の新しいID
  ```

### 2.2 段階的な承認プロセス（ステップ実行）
* **概要**: 複雑なタスクや複数のファイル変更を伴うタスクにおいては、一気に作業を進めず、ステップごとに区切って承認を得ます。
* **ルール**:
  * 「タスク計画の承認」→「実装内容の提示（承認）」→「検証結果の提示（承認）」といった段階的フローを遵守する。
  * ユーザーの承認を得るまでは、次のフェーズ（コミットやデプロイ等）へ移行しない。

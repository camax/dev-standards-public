# 🛡️ Git Safety & Quality Control Protocol

## 1. タスク着手時の安全確保

### 1.1 作業前バックアップコミットの義務化 (Baseline Commits)
* **概要**: 作業を開始する前に、現在の作業コピーの状態を完全にコミット（または退避）して基準点（ベースライン）を明確にします。
* **ルール**:
  * タスクに着手する際は、修正を開始する前の段階で必ずバックアップコミットを行う。
  * コミットメッセージは `chore: backup before [タスク名・タスクID]` のように作成し、いつでも改修前の状態にロールバックできるようにする。

### 1.2 依存関係の事前影響調査
* **概要**: 修正対象のファイルや関数が、他のモールや別アプリ、GASの共通コード等に依存していないか事前に静的・動的解析を行います。
* **ルール**:
  * グローバル共通の関数や定数（例: `KINTONE_FIELD_MAP`）を修正する場合は、事前に `grep_search` 等で依存関係を全て洗い出し、影響範囲を特定すること。

### 1.3 pre-commit フック初回導入時の順序
* **概要**: フックの存在を検査する自動実行スクリプトは、フックの初回導入には使用できない。
* **ルール**:
  * 初回は `dev-standards/hooks/pre-commit` を通常の `core.hooksPath` の配置先に設置し、実行権限と `git config --get core.hooksPath` の値を確認してから自動実行を開始する。
  * フック自身を作成・修正するタスクの最初のコミットも、設置済みフックを通常どおり動かして作成する。存在検査で停止した場合はフックの設置を先に完了し、検査を再実行する。
  * 一時的な `core.hooksPath` の変更や `--no-verify` は使用しない。

### 1.4 安全フック導入時の「鶏と卵問題」の回避
* **概要**: ゴール判定AIループ（`goal_loop.sh` や `vault_goal_loop.sh` 等）は、起動前チェックで安全フック（`.claude/settings.json` の PreToolUse/PostToolUse 等）の存在を要求する設計になっている。しかし「安全フックを導入する」こと自体が `PLAN.md` のタスクである場合、ループ自体がフック未設定エラー（例: `ERROR: .claude/settings.json が無い`）で起動できず詰んでしまう「鶏と卵の問題」が発生する。
* **ルール**:
  * **初回ブートストラップのループ外実行**: 安全フックの初回ブートストラップ（作成・設定）は、ループの外（手動、または単発のCodex/Antigravity実行）で行うこと。AIループに「フックを作らせる」という設計にはしない。
  * **模擬テストの実施**: 初回ブートストラップ後、模擬テスト（例：`rm -rf`・`git add .`・`git reset --hard` 等の危険操作が正しく拒否されるか）で動作確認してからコミット・pushする。
  * **ループの再開**: ブートストラップと動作確認完了後、改めて `goal_loop.sh` / `vault_goal_loop.sh` を起動する。以降は正常に起動前チェックを通過する。
  * **一時的にフックなしで進めてよい条件**: 安全フックが存在しない状態で作業を進めてよいのは、**その作業がフック自体の初回導入タスクに限る**場合のみとする。それ以外の通常タスクでフックが無い状態を「一時的に無視してよい」とは絶対にしないこと。
  * **関連ルール**: フック自体の判定エラーに関する扱いは [1.5 フック判定エラー時のバイパス禁止](#15-フック判定エラー時のバイパス禁止) を厳守すること。

### 1.5 フック判定エラー時のバイパス禁止
* **概要**: 安全フック等の判定によってエラーが発生し処理がブロックされた場合の対応原則。
* **ルール**:
  * **原因特定前のバイパス禁止**: フックの判定結果に関わるエラーは、原因を完全に特定し尽くすまで絶対にバイパス（`--no-verify` 等）しないこと。
  * ※ 1.3の「一時的な `--no-verify` は使用しない」および、2.8「環境乖離・異常検知時の停止義務」とあわせて運用する。

## 2. コミット前の品質管理 (QC監査)

### 2.1 コミット前のセルフチェックリスト
* **概要**: ソースコードをコミットする前に、以下の点を確認します。
  * `console.log` のデバッグ出力が残っていないか
  * 不要なコメントアウトされた旧コードが残っていないか
  * 文字コード（Shift_JISなど）がターゲット環境と合致しているか

### 2.2 QAスキル (anti_regression_protocol) の強制適用
* **概要**: 計算ロジックや共通関数の改修、重要なデータのマッピングを伴う変更の場合、`anti_regression_protocol` スキルを適用し、デグレ防止のプロセスを踏みます。
* **ルール**:
  * 改修前後の動作結果を自動または手動の比較スクリプトで検証し、差分がないことを確認する。
  * WBSチェックリストをタスクログ等に永続表示させ、各項目がすべて完了していることを確認する。

### 2.3 修正後のDiff検証と動作確認ログの取得方法
* **概要**: 意図しない箇所の変更やデバッグ記述の混入を防ぐため、コミット前に必ず Diff を精査し、その検証結果ログをタスクドキュメントに記録します。
* **ルール**:
  * `git diff` を実行して、自分が意図して変更した行のみが変更されているかを1行ずつ確認する。
  * テスト実行結果のコンソール出力や、動作検証スクリプトの出力結果をエビデンス（動作確認ログ）としてタスクフォルダに保存する。

### 2.4 コミットメッセージ規約（Conventional Commits）
* **ルール**:
  * Conventional Commits に従い、type は `feat` / `fix` / `refactor` / `docs` / `chore` のいずれかを使う。
  * タスクIDがある場合は末尾に付ける。例: `fix(import): fix carrier mapping logic in CSV import [PROJ-102]`

### 2.5 完了報告のエビデンス添付義務
* **概要**: コミットや修正の完了報告を行う際は、客観的な証拠（エビデンス）を必ず提示します。
* **ルール**:
  * コミット・修正の完了報告には、必ず `git log --oneline -1` や `git show --stat` 等の生の実行結果を添付する。
  * コマンド出力は要約・再入力（手打ち）せず、必ずそのままコピーして貼り付ける。出力の裏付けがないハッシュ・完了報告を禁止する。

### 2.6 指摘への検証義務
* **概要**: ユーザーから誤りや不整合を指摘された際、事実確認を行わずに鵜呑みにしたり、推測で回答したりすることを防ぎます。
* **ルール**:
  * ユーザーから誤り・不整合を指摘された場合、同意も反論もする前に、必ずコマンドで現状を確認し、生の出力を添えて回答する。
  * 事実確認をせずに誤りを認めること、推測で経緯を説明することを禁止する。

### 2.7 ステージング操作の制限
* **概要**: 意図しないファイルや一時的な作業用ファイルがコミットに混入するのを防ぎます。
* **ルール**:
  * `git commit -am` および `git add .` の使用を禁止する。
  * コミット対象ファイルは、必ず個別のファイルパスを指定して `git add` し、コミット直前に `git diff --cached --stat` で対象ファイル一覧が現在のタスクのスコープと完全に一致していることを確認する。

### 2.8 環境乖離・異常検知時の停止義務
* **概要**: ローカルリポジトリ（Git等）と本番環境のソースコードの間に「アーキテクチャの根本的な違い」や「予期せぬファイルの不整合（例：本番にしかないエンジンが存在する等）」を検知した場合の安全措置を定めます。
* **ルール**:
  * **処理の強制停止**: 上記の不整合を検知した場合は、絶対にそのままコードを出力・上書きしない。
  * **異常報告**: ユーザーに対して **【警告】** と **【原因の推測】** を第一に報告する。
  * **状況確認**: 「なぜこの乖離が発生しているのか（例：本番での直接編集の可能性など）」をユーザーに確認し、指示を仰ぐ。

### 2.9 成功条件駆動 (Success Criteria Driven)
* **概要**: 「動いているつもり」で完了報告してしまう認識齟齬を防ぐため、着手前に検証可能な成功条件を明示し、完了報告はその条件との突き合わせ結果で行います。
* **ルール**:
  * タスク開始時、実装者（Antigravity または Claude Code）は着手前に「成功条件リスト」を必ず出力する。
  * 成功条件は検証可能な形で書く。「動くこと」のような曖昧な表現は禁止し、誰が確認しても同じ判定になる具体的な文で書く（記載例: 「注文取込ボタンで対象サイトの注文が商品コード付きで取り込まれる」。アプリ名・値は各プロジェクトのものに読み替える）。
  * 成功条件リストには、「既存機能が壊れないこと」を確認する具体的な項目を最低1つ含める。
  * タスク完了報告は、成功条件リストの各項目に対して ✅（達成）/❌（未達成）/未確認 のいずれかを付したステータス表を伴わない限り受理しない。各ステータスの裏付けは 2.5（完了報告のエビデンス添付義務）に従い、生の実行結果・検証ログを添付する。

### 2.10 ゲート判断：影響範囲（blast radius）に基づく確認要否
* **概要**: push・削除等の操作における確認要否を感覚的に判断せず、影響範囲と可逆性を軸に客観的に判断します。
* **基本原則**: ゲートは「どれだけ自信があるか」ではなく「間違えた時にどれだけ影響が及び、取り返しがつくか」で置く。
* **確認要否マトリクス**:

| 操作 | 可逆性 | 確認要否 |
|---|---|---|
| trash（ゴミ箱退避） | 可逆 | 自動承認可、事後報告のみでよい |
| 個別ファイルのgit push（テスト・検証済み） | 準可逆（revert可能） | 生ログ添付の上で事後報告でよい、ただし初回は要確認 |
| rm | 不可逆 | 必ず事前確認。原則使用禁止（trashを使う） |
| 複数リポジトリへの横展開push | 準可逆だが影響範囲大 | 必ず事前確認 |
| 本番環境・公開リポジトリへの変更 | 影響範囲最大 | 必ず事前確認、生ログ必須 |

* **既存ルールとの整合性**:
  * **1.1（バックアップコミット）**: いずれの操作であっても着手前のベースラインコミット義務は免除されない。
  * **2.5（生ログ添付義務）**: 「事後報告でよい」とされる操作（trash、個別push等）であっても、実行結果の生ログ添付は必須とする。
  * **2.7（ステージング制限）**: 個別ファイルのpushであっても、`git add .` や `git commit -am` の禁止、個別パス指定、`git diff --cached --stat` の確認は厳守する。

## 3. 着手前の検証設計

### 3.1 検証手順ファースト (Verification-First)
* **概要**: 「実装してから確認方法を考える」順序を禁止し、コード変更前に検証手順（2.9の成功条件を「どう確認するか」）を確定させます。
* **ルール**:
  * コード変更前に、実装者は「この変更が正しいことをどう確認するか」を先に書く。
  <!-- stack:kintone-gas:start -->
  * **GASの場合**: Logger出力での確認ポイント、確認対象のレコードID、dry-run が可能ならその方法（例: 書込処理をコメントアウトしたテスト関数、対象を1件に絞った実行）を記載する。
  * **Kintone JSカスタマイズの場合**: どの画面（一覧/詳細/編集/作成）でどの操作をして、何が表示されれば成功かを記載する。
  <!-- stack:kintone-gas:end -->
  * **検証手順が書けないタスクは、着手前に人間（プロジェクト担当者）に相談して止まる。**

## 4. クライアントリポジトリ運用（GitLab MR運用）

> **適用範囲**: client-delivery プロファイルのみ（internal-only には init.sh が配布しない）。クライアントリポジトリ宛の納品・MR・push を行うときに適用し、それ以外の作業では読み飛ばしてよい。

### 4.1 リポジトリ分離の原則
* **概要**: 内部リポジトリでは全ファイルを管理し、クライアントリポジトリ（.agent/project.md で定義）には納品物のみを置きます。
* **ルール**:
  * クライアントリポジトリに置いてよいのは納品物のみとする。納品物の範囲は `.agent/delivery_allowlist.txt` で定義する。
  * 以下をクライアントリポジトリに含めることを禁止する: `.agent/**`、`CLAUDE.md`、`task/**`、`TASK_LOG*`、内部作業メモ・検証ログ。プロジェクト固有の追加禁止パスは `.agent/delivery.conf` の BANNED_PATTERN で定義する。
  * 納品は専用クローンディレクトリ（.agent/project.md で定義、クライアント正ブランチ起点）からのみ行う。内部リポジトリからクライアントリポジトリ宛に直接pushすることを禁止する。
  * 内部リポジトリから納品ディレクトリへの転送は、許可リストに基づく同期スクリプト（.agent/scripts/sync_to_delivery.sh）経由のみとする。
  * 同期スクリプトは「コピーしたファイル一覧」を出力し、MR作成時の変更ファイル一覧（templates/mr_template.md）の証拠として使う（2.5 エビデンス添付義務との接続）。
  * pre-pushフック（4.4）を内部・納品の両ディレクトリに設置し二重化する。

### 4.2 MR経由の変更フロー
* **概要**: クライアントリポジトリへの変更は、必ず作業ブランチからのMerge Request経由で行います。
* **ルール**:
  * `main` への直接pushを禁止する（クライアント側で保護ブランチ設定済み）。
  * 作業ブランチ命名は `feature/{タスク識別子}-{短い説明}` または `fix/{タスク識別子}-{短い説明}` とし、タスク識別子の規約は .agent/project.md で定義する（記載例: `fix/PROJ-599-shipping-date-guard`）。
  * 1タスク = 1MR とする。MR内のコミットは2.7（ステージング操作の制限）に従って個別ステージングで作成し、原則1タスク1コミットに収める。レビュー対応で追加コミットが生じる場合も、各コミットのスコープはタスク内に限定する。
  * マージ後の作業ブランチは削除する。

### 4.3 MR記載必須項目
* **概要**: MRの説明文に、レビューに必要な背景と検証結果を漏れなく記載します。
* **ルール**:
  * 変更の目的・背景を記載する。
  * 関連チケット番号 / Slackやり取りへの参照を記載する。
  * 動作確認の内容と結果を記載する。形式は completion_report.md の成功条件ステータス表を流用し、内部用語（.agent、ルール番号等）を除いたクライアント向け簡約版とする。
  * 説明文は templates/mr_template.md の形式に従う。

### 4.4 push前の宛先・内容確認
* **概要**: クライアントリポジトリ宛のpush事故（宛先誤り・内部ファイル混入）を機械的に防ぎます。
* **ルール**:
  * クライアントリポジトリのホスト（.agent/delivery.conf の CLIENT_HOST）宛のpushは、pre-pushフックで停止し、意図したpushのみ `CLIENT_PUSH_OK=1` を付けて通過させる。
  * あわせて、push対象の差分に4.1の禁止ファイル（BANNED_PATTERN）が含まれていないかを自動チェックし、含まれていれば拒否する。

## 5. タスク完了時のSlack通知文生成

> **適用範囲**: client-delivery プロファイルのみ（internal-only には init.sh が配布しない）。completion_report.md を出力する完了報告時に適用し、それ以外の作業では読み飛ばしてよい。

### 5.1 適用対象
* **概要**: completion_report.md（成功条件ステータス表）を伴う全タスクを対象とし、特にMR作成を伴うタスク・クライアント向け成果物に関わるタスクで重要度が高い。
* **ルール**:
  * completion_report.md を出力する全タスクで、本節の下書きも併せて生成する。

### 5.2 生成ルール
* **概要**: タスク完了報告の最後に、Slack向け下書きを completion_report とは別ブロックとして併記する。
* **ルール**:
  * 技術的証拠（レコードID、コミットハッシュ、ログ等）は含めない。
  * 「何を」「なぜ」「結果どうなったか」の3行程度に圧縮する。
  * MRを作成した/する予定の場合、MRリンクと「ご確認をお願いします」の一言を含める。ただしMRリンクは作成後の閲覧用URLに限る。MR未作成の段階で下書きを生成する場合は、作成用URL（`/merge_requests/new?...`等）をそのまま送信用リンクとして提示せず、「MR作成後、リンクをお送りします」等その旨を明記する。
  * 絵文字・過度なカジュアルさは避け、クライアント宛にも流用できる中立的なトーンにする。
  * 宛先（社内向け／クライアント向け）によって内部用語（Antigravity、Claude Code、Kintoneアプリ番号等）を含めるか出し分ける。デフォルトは社内向け（用語含む）とし、「クライアント向けに」と指示があればクライアント向け版も出す。

### 5.3 出力形式
* **概要**: completion_report.md の末尾に、決まった見出しで下書きを追記する。
* **ルール**:
  * 以下の形式で追記する。

    ```
    ---
    ### Slack下書き（社内向け）
    （3〜5行の平文）

    ### Slack下書き（クライアント向け・該当する場合のみ）
    （内部用語を除いた平文）
    ---
    ```

### 5.4 送信について
* **概要**: 下書きの生成・提示までを完了報告の範囲とし、実送信は行わない。
* **ルール**:
  * Slackへの実送信はこのルールの範囲外とする。
  * 下書きの生成・提示までを完了報告に含め、送信は担当者本人が行う。

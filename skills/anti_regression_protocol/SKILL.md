# 🛡️ Anti-Regression Protocol (ARP)

このスキルは、コードの修正やリファクタリングにおいて「デグレード（機能後退）」を物理的に防ぐための厳格なワークフローを規定します。
複数のAIエージェント（実行役・レビュー役）が協力して開発する環境で、コードの破損・論理の後退・スコープ外変更を防ぐ標準手順（旧 `safe_development` v2.0）も本スキルに統合しています。

## 1. 起動トリガー
- ファイル修正、機能追加、リファクタリングの依頼を受けた際。
- 複数のAIエージェント（実行役・レビュー役）が協力して開発を行う際。

## 2. 実行ステップ

### 【Step 1: 同期・Gitベースラインの確保 (Sync / Pre-flight Check)】
- 修正対象のファイルが決まったら、**絶対にコードを触り始めないこと。**
- `git status` で未コミットの変更がないか確認する。
- 未コミットの変更がある場合、`rules/git_safety.md` 1.1 のバックアップコミットでベースライン（クリーンな状態）を確立する。これは任意確認ではなく必須の手順とする。レビュー役（人間またはレビュー担当エージェント）がいる場合は、作成後に報告する。
- 必要に応じて `git pull` で最新ベースラインを確保する。

### 【Step 2: 既存ロジックの完全把握 (Logic Inventory / Analyze)】
- 修正が必要なファイルと関数を 1ファイル・1関数 の単位で特定する。
- 対象箇所のロジック・デバッグログ・周辺の依存関係を確認する。
- 修正対象のコードを読み込み、「現在実装されている機能・条件分岐・エッジケース処理」を箇条書きでリストアップし、ユーザー（レビュー役）に提示してから次へ進む。
- 目的：「絶対に壊してはいけない既存機能」を明言し、共通認識を持つため。

### 【Step 3: 実装 (Implement)】
- 指示された内容以外のコードに触れない。
- ローカル実行型のコーディングエージェント（ペアプログラミングツール等）を使用する場合は、対象ファイルを1つのみ指定して実行範囲を限定する。

### 【Step 4: Diff 監査 (Diff Verification)】
- コード修正直後、自ら `git diff`（スコープ確認には `git diff --stat`）を実行する。
- ベースラインと現在の差分を自己レビューし、「意図した変更だけが含まれているか」「Step 2の既存機能が破壊されていないか」を厳格に監査する。
- 監査結果を diff 形式でユーザー（レビュー役）に報告し、承認を得てから次へ進む。

### 【Step 5: 検証 (Verify)】
- 修正後は、そのプロジェクトのビルド/テストコマンド（例: `npm run build`、`xcodebuild`、`pytest` 等）で必ず正常終了することを確認する。
- 既存のデバッグログ（🔍 等の目印）が維持されているか確認する。
- ビルドエラーが発生した場合は即停止してレビュー役に報告する。

## 3. 🚨 緊急停止ルール（即停止・報告）

以下が発生した場合は作業を中断し、レビュー役に報告する。
自己判断でリトライ・修正しない。

1. 指示したファイル以外が変更された
2. git diffが100行を超えた
3. ビルドエラーが発生した
4. 実行役（ローカルLLM／サブエージェント）が3回連続でスコープ違反した → レビュー役がNG判定し、上位のエージェントまたは人間が直接編集に切り替える
5. 実装中に既存設計との重大な矛盾を発見した

## 4. Flash Optimization (WBS Persistence)
- すべての返答の末尾に、現在のタスク進行状況を示す **【🛠️ Logic Inventory Checklist】** を必ず表示すること。
- これにより、エージェント自身のコンテキスト維持と、ユーザーへの進捗の透明性を確保する。

---

> [!IMPORTANT]
> このプロトコルは、他のいかなる作業（スピード優先の修正など）よりも優先されます。デグレードをゼロにすることが最優先事項です。

「慎重さはスピードに勝る。スコープ外は触らない。必ず報告してから進む。」

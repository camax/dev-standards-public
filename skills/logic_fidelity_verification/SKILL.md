# Data Fidelity Assurance Strategy (データ整合性担保プロトコル)

## 目的
重要なビジネスロジック・スクリプトのリファクタリングや移行時における「仕様漏れ（Logic Drop）」および「サイレント障害（Silent Regression）」を防ぐこと。
このプロトコルは、新しいシステムの**出力データ**が、**ビジネス上の意図**（多くの場合、レガシーシステムの挙動によって定義される）と厳密に一致することを検証します。

## プロセス・ワークフロー

### Phase 1: 現状定義（As-Is 解析）
**ゴール**: 「現在何が起きているか」を曖昧さなく定義する。
1.  **レガシーコード監査**: 現在の本番コードを一行ずつ読み解く。
2.  **ロジック抽出**: すべての条件分岐（if/else）、変換（正規表現、計算）、および特殊処理（ハードコードされた例外）をリストアップする。
3.  **フィールドマッピング表**: `元フィールド` から `先フィールド` への対応表を作成する。
    *   *生成物*: `logic_comparison_table.md`（As-Is 列）

### Phase 2: 要件定義（To-Be スキーマ）
**ゴール**: 「正しいデータ」の要件を確定させる。
1.  Phase 1に基づき、すべての入力パターンに対する**期待される出力データ**を定義する。
2.  改善が必要な場合（バグ修正など）は、それらを **「意図的な変更」** として明示的にドキュメント化する。
3.  **合意**: このデータスキーマが「正解（Source of Truth）」であることをステークホルダーと確認する。

### Phase 3: 実装（コーディング）
**ゴール**: Phase 2を満たすロジックを構築する。
0.  コード変更前に、`rules/git_safety.md` 1.1 に従いバックアップコミットを作成する。Phase 4 のスナップショットテストで旧スクリプトを実行する際の基準点にもなる。
1.  定義されたデータスキーマを再現するためのロジックを実装する。
2.  「設定駆動型（Configuration-Driven）」のデザインの場合、Configオブジェクトがフィールドマッピング表を厳密に反映していることを確認する。

### Phase 4: 検証（監査）
**ゴール**: マージ前の必須チェック。
**重要なステップ**: 「コード vs 記憶」ではなく、「出力 vs 要件」を検証する。

1.  **ロジックマトリクス表現**:
    *   Phase 1のすべての項目が新しいコードに存在することを確認する。
    *   結果: `✅ 完全に再現` または `✨ 拡張`。
2.  **フィールド単位の監査**:
    *   `旧フィールドコード` vs `新設定フィールドコード` を比較する。
    *   タイポによるデグレード（例：`OrderDate` vs `OrderTime`）をチェックする。
    *   *生成物*: `field_mapping_audit.md`
3.  **ドライラン / スナップショットテスト**:
    *   同じ入力データに対して新旧両方のスクリプトを実行する。
    *   出力されるJSONを比較する。それらは同一（または「意図的な変更」と一致）でなければならない。

## 使用場面
*   コアな計算ロジック（価格、税金、在庫）のリファクタリング。
*   データマッピング（注文API、CSVインポート/エクスポート）の移行。
*   ユーザーが「以前とまったく同じように動くようにして」と言ったとき。

## 関連スキルとの使い分け
*   `anti_regression_protocol`: 個々の修正におけるGitベースライン確保とDiff監査。本スキルはリファクタリング・移行全体を出力データで検証する。
*   `implementation_fidelity`: デプロイ前に要件の項目がコードに存在するかをgrepで確認する。本スキルは出力結果そのものを比較する。
*   `kintone_ops/mapping_regression_prevention`: Kintone連携の全媒体共通マッピングに特化したスナップショット比較。

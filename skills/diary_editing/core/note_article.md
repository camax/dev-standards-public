# ステップ0 & ステップ1: note用記事の生成ルール
 
 **【ステップ0：原文バックアップ & 直近事例録の確認（必須・最優先）】**
 - **編集前の絶対義務:**
   1. 元のObsidianファイル（原文の音声入力テキスト）を必ずGitコミットすること（事前に `OBSIDIAN_ROOT` にVaultのルートを設定。例: `git -C "$OBSIDIAN_ROOT" add <ファイル名> && git -C "$OBSIDIAN_ROOT" commit -m "backup: 原文 <YYYYMMDD>"`）。
   2. `{editing_log_dir}/` 内の**最新の事例録（直近のAIプロンプティング事例録）を必ず読み込む**こと。「AIが無意識にディテールを削ってしまいダメ出しされた過去の失敗」を毎回作業直前に強制的にリマインドし、要約バイアスを事前に遮断する。

 **【ステップ1：物理的工程分離（2パス生成方式）】**
 「整形」という指示がAIの頭の中で「要約」にすり替わるのを**構造的・物理的に不可能にする**ため、生成プロセスを完全に2つのパスに分離して実行する。

 - **パス1（機械的コピー ＋ 改行・空行挿入のみ）:**
   - 原文の一字一句を完全に維持し、文の削除・要約・言い換えは**物理的に一切行わない**。
   - 行う操作は「1〜2文ごとの句点での改行・空行の挿入」および「明らかな誤字脱字・音声認識エラーの最小限の修正」のみ。
   - 原文のセンテンスは1つたりとも落としてはならない。
 - **パス2（構造化 ＋ 見出し・あらすじ付与 ＋ 改善提案の分離）:**
   - パス1で作成された「原文100%保持テキスト」に対して、ブロックごとの見出し（`###`）と区切り線（`---`）、タイトル（H1）、あらすじ、末尾フッターを付与する。
   - **表現改善の提案分離:** もし表現の不自然さや言い回しの改善点がある場合、**本文を勝手にリライトすることは禁止**。本文はそのまま維持し、報告欄に「【表現改善の提案】原文のこの箇所は、こう修正することも可能です」として別枠で箇条書き提示し、採用は100%ユーザーに委ねる。
 
 - **上書き前の確認義務:** ステップ0のGitコミットが実際に成功していることを `git log -1 --oneline <ファイル>` 等のコマンドで確認してから、本ステップの上書き保存に進むこと。コミットが確認できない場合は、上書きを行わずユーザーに報告する。

 - **ファイル書き込みの徹底:**
   - 生成したnote用記事は、対象のObsidianファイル（例: `YYYYMMDD.md`）の全体を上書きして保存すること。ユーザーへの提示と同時にファイルの更新を完了させておく（※権限エラー等で直接書き込めない場合も、スクリプト実行等を用いて確実に当該ファイルを更新する）。

**【構成フォーマット】**
以下の順序とマークダウンで出力する。

1. **タイトル（Markdown H1見出し ＋ 日付形式）**
   - 冒頭に `[ノート更新]` ではなく、MarkdownのH1見出しタグ（`# `）を付け、「`# YYYY年MM月DD日_そのタイトル`」の形式で出力する（アンダーバー区切り、記事全体を表す惹きの強いタイトル）。
     - 例: `# YYYY年MM月DD日_カフェでの出会いと長年の課題だった制作の完成`
2. **`### 📝 あらすじ`** （見出し）
   - あらすじの本文は、引用ブロック（`>`）や太字装飾（`**`）を使用せず、**通常のテキスト（標準の太さ）** で出力する（可読性重視）。
   - **定型文の挿入（必須）:** あらすじ本文の最冒頭には、必ず `note_intro` の定型文を1行目に配置し、空行を挟んでから当日の要約文を記述すること。
   - **コンパクト化と惹きの重視（必須）:** 1日の出来事を時系列で網羅・解説する冗長な要約は禁止。「定型文」＋「2〜3ブロック程度の簡潔な構成」にまとめ、前半の葛藤やハプニングと後半のハイライトを対比させ、読者が「本文を読んでみたい」と思わせるフック・余韻を最優先すること。
3. **区切り線（`---`）**
4. **本文（エピソードごとのブロック）**
   - 本文は「時間経過があった時」「場所が変化した時」「話題が明確に転換した時」のいずれかを基準としてブロックに分け、それぞれのブロックの前に **区切り線（`---`）** と **H3見出し（`###`）** を挿入する。
   - **見出し命名規則（感情×出来事）:** 抽象的な要約（例「朝の散歩」）を禁止し、「夕方の突然の雨と企画の見直し」のようなキラーワードを前面に出す。また、コロン（：）による区切り自体を用いず、助詞（と・で・における等）で繋いだ単一の句として表現すること。大げさな装飾語（『〜の衝撃』『〜で吹き飛ぶ葛藤』『〜への執念』等）そのものを使わず、具体的な固有名詞・出来事のみで簡潔に表現すること（20〜30文字前後を目安とする）。
5. **フッター（必須）**
   - 本文の末尾に必ず **区切り線（`---`）** を挟み、以下のフォーマットでPodcastリンクとタグを出力すること。
   ```markdown
   ### ▼ Podcastはこちら

   - **YouTube:** <{podcast_urls.youtube}>
   - **Spotify:** <{podcast_urls.spotify}>

   ### タグ

   #今日の振り返り #中心テーマ1 #中心テーマ2 #具体的固有名詞
   ```

**【ハッシュタグ選定の大原則】**
- **目的:** 本文のキーワード全羅列ではなく、「この記事が何の記事なのかを、読者とnote側に少数のラベルで伝える」こと。水増しではなく記事内容と読者のマッチングを最優先とする。
- **最終タグ数:** **原則3〜5個（通常3〜4個、最大5個ハード上限）**。3個で十分なら3個で終了し、無理に5個まで枠を埋めない。
- **読者納得チェック:** 「このタグから記事を見つけた読者は、記事を読んで“このタグの記事だった”と納得できるか？」にYESと言えないタグは絶対に採用しない。
- **完全排除・禁止事項:**
  - ❌ `#日記` `#日常` `#note` の常時自動付与を完全廃止（特に `#note` は禁止）。
  - ❌ 本文に一瞬出ただけの言葉のタグ化禁止。
  - ❌ 近縁語・同義語の水増し禁止（例: `#原付二種 #125cc #バイク #ツーリング` を並べず1〜2個に厳選）。
  - ❌ 「追加候補:」の出力禁止。最終採用タグのみを出力。

# Comparative Schema Analysis Skill

## 🎯 目的
新しい連携先（例：新モール、新サービス）の実装を行う際、**「既存の類似モデル（成功パターン）」を徹底的に分析・模倣**することで、仕様漏れや手戻りを防ぎ、最初から完成度の高い実装計画を策定する。

## 🚦 トリガー
- 新しい外部連携先の追加要件が発生した時
- 既存アプリに新しい種別のデータ管理を追加する時
- ユーザーから「〇〇のような機能を追加したい」と依頼された時

## 🔄 実行プロセス

### Phase 1: 参照モデルの選定 (Determine Reference Model)
実装対象に最も近い「既存の成功モデル（Reference Model）」を選定する。
*   例：新しい連携先Cを追加する場合 → 既に安定稼働している連携先A・Bの実装が参照モデルとなる。

### Phase 2: 全量スキーマ・スキャン (Full Schema Scan)
推測でフィールドリストを作るのではなく、スクリプトを使用して参照モデルの全フィールド実態を調査する。

**推奨コマンド例:**
```bash
# 対象アプリの全フィールドを取得し、参照モデルのキーワードでgrepする
node debug_fetch_fields.js --app <APP_ID> | grep -i "<reference_keyword>"
```
*注意: `debug_fetch_fields.js` は本リポジトリには同梱していません。各プロジェクト側で別途用意する前提です。*
*   **Checkpoints:**
    *   金額系であれば `売価` だけでなく `売上`、`利益額`、`利益率` はあるか？
    *   `備考`、`ステータス`、`掲載期間` などの管理フィールドはあるか？
    *   `税抜` / `税込` のペアは存在するか？

### Phase 3: ミラーリング提案 (Mirroring Proposal)
スキャン結果に基づき、参照モデルにあるフィールドのうち実装候補となるものを洗い出し、**提案としてユーザーに提示する**。採否は過剰実装を避ける観点も踏まえ、最終的にユーザーが判断する。

*   **Action:**
    *   実装計画書（Implementation Plan）に、参照モデルとの対比表を作成する。
    *   各フィールドについて「なぜ必要と考えられるか」を添えて提案し、実装するかどうかの判断をユーザーに仰ぐ（自動的に全て実装する方針にはしない）。

### Phase 4: 実装前検証 (Pre-Implementation Verification)
提案または実装前に、APIを用いて実際のアプリ構造を確認し、机上の空論（Configファイルのみの修正）になっていないかを確認する。

*   **Action:**
    *   Debug用スクリプトを実行し、実際のフィールドコードやAPIトークン権限を確認してから実装報告を行う。

## 📝 エージェントへの指針
*   **「たぶんこれだけで動く」は禁止**。常に「既存はどうなっているか？」を確認せよ。
*   ユーザーの要望が「最小構成」であっても、プロとして「運用上これらも必要になりますが、追加しますか？」と提案せよ。

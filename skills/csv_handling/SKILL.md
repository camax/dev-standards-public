# 📊 CSV Handling Strategy (skills/csv_handling/SKILL.md)

## 1. 発動条件
* **CSVの入出力・パース・生成を伴うコード修正・機能追加を検知した場合に発動。**
* 該当タスクに着手する前に必ず本ドキュメントを読み込み、以下のチェックリストを遵守すること。

---

## 2. 必須チェックリスト

* [ ] **1. 文字コード・BOMの整合性確認**
  * 入力元（インポートファイル）および出力先（エクスポートファイル）の文字コード（`Shift_JIS`, `UTF-8`）および BOM（Byte Order Mark）の有無を確認し、整合性が保たれているか。
  * **【確認方法】**: `file --mime-encoding <ファイル>` または `od -c` で BOM(EF BB BF)有無を確認。
* [ ] **2. 先頭ゼロ欠落対策（ゼロ埋め補正）**
  * 電話番号、郵便番号、SKU、顧客コードなど、先頭に `0` が含まれる可能性のある項目に対し、Excel等を経由した際に `0` が自動的に欠落する前提でパース・出力処理を行っているか。
  * **【確認方法】**: サンプルCSVの該当列を `head` で目視し、桁数固定項目は `grep -E` で桁数チェック。
  * **【過去の障害実例】**: 実例: 電話番号先頭ゼロ欠落障害（Excel経由CSV起因、normalizeTel() を複数GASファイルに展開して対応）
* [ ] **3. キー項目のバリデーションと破損データ検知**
  * SKUや注文番号等の必須キー項目の形式をチェックし、破損データや不正データを検知した場合は**処理を安全に即時中断（フェイルセーフ）**し、**対象行番号を含めた詳細な診断ログ**を出力しているか。
  * **【確認方法】**: テストCSVに意図的な破損行を1行混入させ、中断＋行番号ログを確認。
  * **【過去の障害実例】**: 実例: App568 破損CSV混入障害（回収ボタン動作不能。SKUバリデーション追加と診断ログ強化で対応）
* [ ] **4. 想定外フォーマットに対する安全策**
  * ヘッダ行の項目不一致、または想定外の列数（カラム数）のデータが混入した際、プログラムが例外で落ちる前に検知し、処理を安全に中断して適切なエラーログを出力しているか。
  * **【確認方法】**: 列数の異なるテストCSVで即時中断を確認。
  * **【過去の障害実例】**: 実例: App568 破損CSV混入障害（回収ボタン動作不能。SKUバリデーション追加と診断ログ強化で対応）
* [ ] **5. 改行コード・囲み文字の確認**
  * 改行コード（CRLF / LF）が入力元・出力先の仕様と一致しているか。また、ダブルクォート囲みフィールド内のカンマ・改行・エスケープされたクォート（""）を正しく処理できるパーサを使用しているか。（単純な `split(',')` / `split('\n')` の使用を禁止する）
  * **【確認方法】**: `od -c` で CRLF(\r\n)を確認、カンマ入りフィールドのテストケースでパース結果を確認。

## 3. 詳細解説

### 3.1 文字コードとエンコーディングの選定
* **Shift_JIS (CP932)**:
  * 主に国内の古い基幹システムや、日本の伝統的なECモールのアップロード仕様で要求されます（例: ベネフィット・ワン消込CSV等）。
  * Kintone JavaScript内またはGAS内で文字コード変換を行う際は、変換時の文字化け（波ダッシュ `〜` や丸数字 `①` 等の機種依存文字）を考慮してください。
* **UTF-8 (BOMの有無)**:
  * Excelで直接開いた際に文字化けを起こすのを防ぐ目的で、出力CSVに UTF-8 BOM (`\ufeff`) を付与するルールが指定されているか（またはその逆でBOMなしを求められているか）仕様書を確認してください。

### 3.2 先頭ゼロ欠落（ゼロサプレス）の対策
* **発生要因**:
  * ユーザーがインポート用CSVを Excel 等で一度編集・保存すると、文字列型の「090...」「0001...」が数値型に自動変換され、「90...」「1...」のように先頭の `0` が消去（ゼロサプレス）されます。
* **実装方針**:
  * 入力値を処理する際は、必ず文字列としてキャストし、必要に応じて適切な桁数で `padStart()` によるゼロ埋めを行います。
  * 電話番号や郵便番号に関しては、既存の `normalizeTel()` や `normalizeZip()` などの正規化ヘルパー関数を通し、自動補正をかけてから保存・利用します。

### 3.3 キー項目バリデーションと破損レコード対応
* **検証のタイミング**:
  * CSVを1行ずつループ処理する際、行単位でキー項目（`SKU`, `注文番号`, `送り状番号` 等）のバリデーションを挟みます。
* **フェイルセーフ処理**:
  * **デフォルトは処理全体の即時中断**とします。行スキップによる部分続行は、仕様書に明記がある場合に限る例外とし、スキップした行番号・内容を必ず診断ログに残します。
  * ログ出力例:
    ```javascript
    console.error(`[Error] CSV Row ${rowIndex} validation failed. Missing SKU. Row content: ${JSON.stringify(row)}`);
    ```

### 3.4 列数およびヘッダの厳密チェック
* **フォーマット防御**:
  * CSVパース後、最初の処理（ヘッダ解析）の段階で、必要な列数が揃っていること、ヘッダ文字列が想定と一致していることを厳密に検証してください。
  * 列数やヘッダに過不足がある場合は、処理を即座にエラーとし、後続のデータベース（Kintoneレコード）書き換え処理が絶対に走らないように安全ガードを敷いてください。

### 3.5 改行コードと囲み文字（ダブルクォートエスケープ）の解析
* **改行コードの判定**:
  * Windows環境や多くのECシステム（楽天等）から出力されるCSVは CRLF (`\r\n`)、Linux/macOS環境のデフォルトは LF (`\n`) です。入出力のターゲット環境がどちらを求めているか検証し、不要な `\r` を取り除く、または正しく付与して書き出してください。
* **高度なCSVパーサの利用義務**:
  * CSV内のフィールド自体にカンマや改行、エスケープされたダブルクォート（`""`）が含まれる場合、単純な `split(',')` や `split('\n')` では構造が破損します。
  * 必ず Kintone JS / GAS 環境に適した堅牢なパーサ（例: `PapaParse`、または同様の仕様を満たす汎用正規表現パーサ）を使用してください。

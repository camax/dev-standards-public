# Implementation Fidelity Check (実装整合性チェック)

## 目的
「解析/要件定義書は正しかった（例：正しいフィールド名・パラメータ名を特定していた）が、最終的に実装されたコードにそれが反映されていなかった、あるいは古い状態に戻ってしまった」という特定のデグレード（先祖返り）を防ぐこと。

## 発動トリガー
- 本番環境への **デプロイ（Deployment）** 前。
- **タスク（Task）** の完了・クローズ前。
- 特に **リファクタリング（Refactoring）** や **マージ（Merge）** 処理の直後。

## 手順

### 1. 正解の定義（Identify Source of Truth）
このタスクのロジックを定義した特定の解析ドキュメントまたは要件定義書を特定します。
*   *例: `task/20260116_.../Analysis.md`*
*   *重要項目の例: 「外部連携先Xは項目 `recipient_name` を使用する」*

### 2. 監査項目の抽出（Extract Key Claims）
ドキュメントから、変更に関連する具体的な「必須ロジック要素」を抽出します。
*   **フィールド名/パラメータ名**: 解析で特定された正確な項目コードがコード内に存在するか？
*   **条件式**: 要件定義にある `if` 条件が実装されているか？
*   **値**: ハードコードされたIDや定数が正しいか？

### 3. コード実査（Code Grep Audit）
実際のターゲットファイル（差分ではなく、**ファイル全体の内容**）に対して、抽出した項目を検索（grep）します。

```bash
grep -n "recipient_name" path/to/target_script.js
```

### 4. 判定（Verdict）
- **✅ 合格 (PASS)**: 解析で定義された通りに、コード内に項目が正確に存在する。
- **❌ 不合格 (FAIL)**: 項目が見つからない、コメントアウトされている、あるいは異なっている。
    - **アクション**: デプロイを **停止** してください。コードが解析結果と同期していません。検証失敗です。

### 5. 【追加義務】ランタイム実装整合性チェック（Read-After-Write）の組み込み
外部システム（SaaS API、ノーコードツールのデータベース等）へのデータ連携処理を新規作成、または修正する場合は、単なるコード実査だけでなく、**プログラムの実行時（ランタイム）に本当にデータが到達したかを保証する仕組み**を必ず実装に含めてください。
*   **必須の仕組み**: データの投入処理（`POST/PUT`）が完了した直後に、投入時に発行・使用したIDやキーを用いて投入先へ再取得（`GET`）を行い、「投入したつもりの件数・内容」と「実際に連携先に存在する件数・内容」が一致するかを検証する。
*   **ログ出力**: 件数・内容が一致した場合は `【検証OK】連携先に正しく XX 件のデータが作成されていることを確認しました。` といった明快な成功ログを出力し、不一致や通信エラー時は `【検証NG】` としてアラートを上げるロジックを必ず盛り込むこと。
*   **目的**: APIのステータスコード200（通信成功）を鵜呑みにせず、実際の登録件数ベースでのデータ到達を保証し、「プログラム上は成功したが連携先には入っていない」という事故を未然に防ぐ。

## 自動チェックスクリプト（任意）
`requirements.json` やフォーマットされたリストがある場合は、自動化が可能です。

```javascript
// 簡易監査スクリプトの例
const fs = require('fs');
const code = fs.readFileSync(TARGET_FILE, 'utf8');
const requirements = [
  { term: 'recipient_name', desc: '配送先の氏名フィールド' },
  { term: 'MD004', desc: 'Markdown Lint ルール' }
];

requirements.forEach(req => {
  if (!code.includes(req.term)) {
    console.error(`[FAIL] 要件不足: ${req.desc} (${req.term})`);
    process.exit(1);
  }
});
```

# 稼働中プロジェクトへの後付け適用

init.sh は `.agent/` が既に存在すると中断する（新規プロジェクト専用）。
update.sh は既存の `.agent/` が dev-standards 由来であることを前提に同名上書きする。

どちらも当てはまらないケース — **`.agent/` は既にあるが、dev-standards 由来ではない**
（別の目的で作られたスキルや設定が既に稼働している）場合の手順を以下に示す。
2026-07-10 にパーフェクトライフログへ internal-only プロファイルを適用した際に
実際に踏んだ手順をそのまま手順化したもの。

自動化スクリプト（apply.sh 等）は用意していない。既存資産との衝突判断は
人間の目視確認が要るため、抜粋生成（プロファイルに応じた rules の抜き出し）
だけを dry-run で得られるようにし、配置は毎回手動で行う。

## 手順

### 1. 既存の `.agent/` を確認する
```bash
cd <対象プロジェクト>
git status --porcelain          # 未コミットの変更がないか確認
find .agent -type f | sort
cat CLAUDE.md 2>/dev/null       # 存在するか、何を import しているか
```
既存の内容が dev-standards 由来かどうかをここで判断する。由来が分かる場合
（同名ファイル・同じ書式）は update.sh の対象なので、この手順書は不要。

### 2. 抜粋を dry-run で生成する
ファイルは一切作成せず、配布されるはずの内容を標準出力に印字するだけ。
```bash
<dev-standardsのパス>/project_template/init.sh --print-rules --type=<client-delivery|internal-only> --stack=<kintone-gas|other>
```

### 3. 衝突ファイルを個別に判断する
`--print-rules` の出力を見ながら、`.agent/rules/git_safety.md` などの配置先ごとに
以下のいずれかを選ぶ:
- 既存に同名ファイルがない → そのまま新規作成してよい
- 既存に同名ファイルがある → 中身を見比べて手動マージするか、配置を見送るかを判断する
- 既存の別ファイル（例: 別の skill）とは無関係 → 触らずそのまま残す

このとき、dev-standards 側にない独自ファイル（例: パーフェクトライフログの
`.agent/skills/requirements_evolve/SKILL.md`）を削除・上書きしないこと。

### 4. CLAUDE.md を追記するか新規作成するか判断する
- CLAUDE.md が存在しない → internal-only なら `@.agent/rules/git_safety.md` /
  `@.agent/rules/antigravity_qc_checklist.md` の2行を持つ新規ファイルを作成してよい。
  既存の `.agent/skills/` 等への参照があれば「必要時に参照」として併記する。
- CLAUDE.md が存在する → 既存の内容を壊さない形で、上記の `@-import` 行が
  含まれているかを確認し、なければ追記する（自動書き換えはしない）。

### 5. 非破壊確認
```bash
git diff --stat            # 追加ファイルのみで、既存ファイルの変更・削除がないか
git status --porcelain     # 意図しないファイルが混ざっていないか
```

### 6. 小さめのタスクで動作確認する
2.9（成功条件駆動）が実プロジェクトで機能するかを、小さく安全なタスクで確認する。
- 着手前に検証可能な成功条件リストを提示する（曖昧語禁止、非破壊確認を1項目含める）
- タスクを実行する
- 完了報告を成功条件ごとの ✅/❌/未確認 ステータス表で提示する（証拠を添えて）

## この手順の位置づけ

この手順書は、後付け適用の実例が積み上がり共通パターンが安定したと判断できた
時点で、自動化（apply.sh 等）を検討するための土台とする。木村看板で2件目の
実例ができた段階で本手順書を見直す。
